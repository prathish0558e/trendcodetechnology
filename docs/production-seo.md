# Production, SEO, and Search Console checklist

The app remains a React/Vite single-page application with the existing Express API. The public site origin is centralized as `https://tctechs.in`; local Vite and Express run together without changing the production API origin. The Express static fallback also serves the generated route documents when using `npm start`.

## Local development

1. Install dependencies with `npm install`.
2. Copy `.env.example` to `.env` if you need to override the public origin or API proxy.
3. Copy `server/.env.example` to `server/.env` and set local mail/database values only when needed.
4. Run `npm run dev`.

The Vite proxy sends `/api` requests to `http://localhost:4000` by default. Set `VITE_API_PROXY_TARGET` to point to a different local API. Set `VITE_API_BASE_URL` only when the API is intentionally hosted at a different origin; leave it blank for Vercel's same-origin `/api` routes. Development pages emit `noindex, nofollow` metadata.

## Vercel project settings

The existing Vercel build and output settings are retained. The build now generates per-route HTML metadata, `robots.txt`, and `sitemap.xml` after Vite finishes.

Set or confirm these environment variables in **Vercel → Project Settings → Environment Variables**:

| Variable | Production value / action |
| --- | --- |
| `VITE_PUBLIC_SITE_URL` | `https://tctechs.in` |
| `PUBLIC_SITE_URL` | `https://tctechs.in` |
| `VITE_API_BASE_URL` | Leave blank when using the same-origin `/api` routes |
| `MONGODB_URI` | Production Atlas connection string, if MongoDB is used |
| `ADMIN_USER` | The verified administrator login email |
| `ADMIN_PASS_HASH` | A real bcrypt hash for the admin password. Login fails closed when this is absent or invalid; there is no built-in password. |
| `ADMIN_TOKEN` | A long random secret used to sign resume download links |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `NOTIFY_EMAIL` | Verified production email settings |

Do not commit `.env` or `server/.env`. `ADMIN_PASS_HASH` and `ADMIN_TOKEN` are server-only; do not prefix them with `VITE_`. The repo deliberately does not inspect or modify a local secret file.

Build and verify before deployment:

```sh
npm run build
npm run seo:check
```

Vercel preview deployments are useful for checking each route's response source and metadata before production. The route rewrites should return the generated HTML for known public routes while preserving the existing SPA fallback for unknown paths and the existing `/api` function routing.

## Search Console setup after deployment

1. Add the **Domain** property `tctechs.in` in Google Search Console.
2. Complete the DNS TXT verification token that Google provides. That token belongs in DNS; it is not generated by this repo.
3. After the production build is live, inspect the homepage and several deep URLs (for example `/services/web-development`, `/careers/it`, and `/contact`) with URL Inspection. Confirm Google can fetch the route, sees the canonical on `tctechs.in`, and does not report `noindex`.
4. Submit `https://tctechs.in/sitemap.xml` in the Search Console Sitemaps report.
5. Recheck indexing and crawl reports after Google has had time to recrawl the site.

`npm run seo:check` verifies the generated files and route configuration locally; it cannot verify DNS, Vercel environment variables, Search Console ownership, or the deployed response. Search appearance and rankings are controlled by Google and are not guaranteed by metadata or structured data.

## Adding a route

Add the route and its unique title/description in `src/seo/routes.js`. Routes with a path parameter need a matching Vercel rewrite in `vercel.json`. The build generates the route HTML, sitemap entries include only indexable routes, and `npm run seo:check` fails if metadata or rewrite coverage is missing.
